## LLM

- ニューラルネットワーク
  - 単層パーセプトロン 1950年代
  - 2012: AlexNet
    - 多層アーキテクチャ
  - ディープラーニング
- エージェントにとってコンテキスト内でアクセスできないものは存在しない
- エージェントにとってリポジトリ内で発見できる古い情報は、最新の真実と区別できない
- 機械学習
  - ニューラルネットワーク、Transformer も機械学習の1種
- GPT
  - **Generative Pretrained Transformer**
- Transformer
  - Encoder
    - ここの発展系が BERT
  - Decoder
    - ここの発展系が GPT
- LLM のトークン出力
  - テキストを入力に、それに続く1つのトークンを出力する処理の繰り返し
- decoder model
  - Tokenize
    - テキストのトークン化
  - Embedding
    - トークンをベクトルに変換
  - Loop
    - Self Attention
      - トークン同士の関係性の計算
    - Feed Forward
      - NN 内部の知識とトークンの関連付け
- Tokenizer
  - GPT: Byte Pair Encoding (BPE)
    - **出現頻度が高いものほど大きなまとまりのトークンになる傾向**
    - => **単語単位でトークン化される場合もあれば文字単位の場合もある。マイナーな言語だとバイト列に分割されることもある**
  - トークン単位で処理が走る
    - => **速度・コストにモロに影響する**
- Embedding
- Self-Attention
  - 以下の2つは『鳥』のトークンの意味が異なる
    - 鳥取県に旅行に行く
    - 鳥が空を飛んでいる
  - 前後の文脈（トークン）から暗黙的に意味を切り替えている
  - Transformer
    - 入力の**全トークンの**関係性を一気に並列計算することが可能
- Feed Forward
  - ニューロン層の積み重ね
- 学習
  - Pre-training
    - テキストの続きを予測する、のみ
  - SFT: Supervised Fine Tuning
    - 人間が作成したプロンプトと回答のペアを学習する
    - **対話能力の獲得**
  - RLHF: Reinforcement Learning with Human Feedback
    - 人間のフィードバックを報酬として、強化学習でモデルをさらに訓練する
    - **人間の好みに合わせた応答の獲得**
  - **対話型 LLM**
    - 特殊トークン `<|user|>` と `<|assistant|>` などを使って、**どの立場の入力かを判断している**
      - ロールの付与
- Few shot Prompting
- **Lost in the Middle**
  - **末尾 > 冒頭 > 中盤** の順番で注意を払っている
- **Reasoning model**
  - 回答を出すまでに**思考過程を出力しながら、コンテキストを充実化させつつ論理を磨いていく**
  - Reasoning モデルは比較的ロングコンテキストに強い

## RAG

- Retrieval Augmented Generation
- 一般的なフロー
  - Function Calling で LLM にしよう判断をさせる
  - **Reasoning モデルを使って MCP に対応したツールでの検索**
- 検索システム
  - フルテキスト検索
    - インデックスの構築
      - 転置インデックス
    - クエリ解析 + マッチング
    - 関連どの計算
      - TF-IDF/BM25 スコアリング手法
  - ベクトル検索
    - Embedding モデル
      - **LLM ベースのベクトル化モデル**
    - LLM の発展とともに注目が高まってきてる
    - ステップ
      - 検索対象ベクトルの生成と格納
      - クエリと検索対象テキストのマッチング
        - 近傍探索のためのアルゴリズム
          - HNSW
    - **ベクトル検索の弱点**
      - 固有名詞への弱さ
        - IP アドレスや電話番号
        - **記号的な情報の扱いが苦手**
      - 類似度の意味の曖昧さ
      - 解釈・デバッグが困難
- **ハイブリッド検索**
  - 同一のクエリに対してフルテキスト検索とベクトル検索を並行して実行
  - => それぞれの結果を統合してランキングの決定
- **リランク**
  - 意味の類似やワードの一致でも読み取れない、**クエリの『意図』を考慮する方法**
  - **検索エンジンから取得した初期結果を LLM を使って再評価・再順序づけする方法**
  - 専用モデル
    - Cohere Rerank
    - Qwen-Reranker
- RAG のチューニング
  - ハイブリッド検索・リランク
  - フィルタ付き検索
    - 対象の範囲を限定する
    - **検索対象のレコード側にも事前にメタデータとしてカテゴリ情報を付与する必要がある**
    - KB での metadata.json
      - https://aws.amazon.com/jp/blogs/news/knowledge-bases-for-amazon-bedrock-now-supports-metadata-filtering-to-improve-retrieval-accuracy/
  - クエリ加工・拡張
    - **タイプミスの修正**
      - 思ってる以上にユーザーはタイプミスをする
    - 知識補完
      - e.g.)
        - チャットbotが嘘をつかないようにしたい => bot ハルシネーション 対策
    - Step Back
      - **上位の概念を一旦出力**
    - 複数クエリの生成
- 中間形式のテキスト
  - Markdown がよか
  - 表など構造が入り組んでる部分は HTML
  - 図はナレッジグラフ or JSON
- HOW
  - PDF
    - Searchable PDF, Image PDF のどちらも LLM での画像解析が良い！
    - Azure Content Understanding
      - https://learn.microsoft.com/ja-jp/azure/ai-services/content-understanding/
  - Word
    - Pandoc
  - PowerPoint
    - LLM によるマルチモーダル画像解析
- Garbage In, GarbageOut
- **チャンク化**
  - Why チャンク化
    - 元々コンテキストウィンドウが小さかった
    - **複数のトピックがあると Embedding 時に意味が希薄化してしまう**
  - Problems
    - チャンク境界による情報・文脈の欠如
      - オーバーラップさせても、背景情報など限界がある
    - 図表の取り込み不良
    - 長文対応 LLM の進化とミスマッチ
- Embedding モデル
  - ドメイン固有の言語や新語だとキーとなる情報が欠落している可能性がある
- CAG: Cach-Augmented Generation
  - 外部知識を LLM のコンテキストに取り込む手法という意味で RAG と一緒
  - RAG:
    - オンラインで外部からデータを取得
  - CAG:
    - **あらかじめ用意されたコンテキストを LLM に渡しておく**
  - **コンテキストウィンドウが大きくなったこと + 小ンテキストキャッシュが効くこと**
- Graph RAG
  - **複数のデータソース間で関連性を見出したいユースケース**
    - サマリーされてないが複数を加味して回答がいる

## Agentic workflow

- エージェントの特徴
  - 目標指向
    - 与えられた目標に向かって処理を遂行
  - 自立性
    - 人間の介入を最小限に抑える
    - 独立してツールの活用順序・パラメータを生成して計画
  - ツール利用
  - 自己評価・修正
- **プロンプトベースエージェント**
  - Reasoning モデルとツール
    - 簡単な AI エージェントになってる
  - タスク状態の明示的な管理は難しい
  - 課題
    - ツール選択の精度低下
    - 手順の誤り
    - 制約の無視
  - 対策
    - プロンプトの改善
    - 宣言型ワークフロー化によるタスク分割
      - LLM の苦手なルールベースの処理・順序制約の強い処理を一部切り出す
      - 事前定義したワークフロー化してコンテキストを分散させる
    - AI エージェントの独自開発
      - タスクの範囲を『宣言型ワークフロー』よりも拡張したい場合
- AI エージェント分割判断
  - 順序制約
  - コンテキストの独立性
  - ツール境界
  - 失敗時の切り戻し
  - 品質評価
- **エージェントのためのデータ**
  - **組織内のデータに関しては、人間よりも AI エージェントからのアクセスの方が圧倒的になる**
  - **データの品質が悪ければ生産性に直結する。。**
  - LLM フレンドリーなデータおよびそのアクセスの仕組みづくり
- UI/UX 設計
  - 起動条件を定める
  - ユーザーから得る小ないってんテキストの設計
  - ユーザーの待機時間設計
  - Human in the Loop
  - 作業状況の可視化
    - ステータス・ログ
    - 通知
- `tool_choice="required"`
- LLM のタスク終了判定
  - ターン数制限
  - 人間の完了判断
  - LLM による完了判断
  - 終了条件スキーマ充足判定
  - テストケース実行
- コンテキスト問題
  - ツール肥大化
    - Tool Search Tool
  - Skills
    - 段階的コンテキストロード
    - Skill 用のサンドボックス環境で、マルチターンでのファイルロード・実行が可能
    - **メインのエージェントがコンテキストを獲得する、という点は残る**
- コンテキストカットで比較
  - MCP (LLM によるツール使用)
    - ツール定義をコンテキストに含めておく
    - コンテキストの肥大化のリスクが高い
      - => シンプルな処理が求められる
  - Skills
    - 段階的にコンテキストを読み込む
    - メインエージェントにコンテキストが載っても良いがただんで複雑なサブタスク
  - エージェント分割
    - コンテキストを分離して別エージェントに任せる
    - 比較的重厚なサブタスク
